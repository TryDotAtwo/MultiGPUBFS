# CayleyPy distributed BFS: ownership, closure, and output contract

## Question

Does retained CayleyPy `BfsDistributed` implement the same ordinary BFS layer
recurrence as the single-device path, and where are novelty and completion
decided?

This is a source audit of `cayleypy/algo/bfs_distributed.py` together with the
dispatch in `cayleypy/cayley_graph.py`. It concerns the library's ordinary BFS,
not its beam-search outer loop.

## 1. Two physical backends, one intended recurrence

The public distributed entry selects:

- a single Python process controlling several CUDA devices; or
- one process per rank under `torchrun`, using `torch.distributed`/NCCL.

Both intend to compute, for each completed layer,

```text
F_(d+1) = unique(expand(F_d)) minus seen.
```

They differ in transport mechanics, gathering, and hook behavior. They do not
change the declared unit-edge distance metric.

## 2. Ownership is a hash partition

The owner rule is

```text
owner(h) = h mod number_of_workers.
```

In the single-process backend, candidate states and hashes are copied into
per-device owner buckets. Under `torchrun`, every rank sorts candidates by
owner and calls `all_to_all_single` separately for hashes and flattened state
payloads.

After routing, one owner receives all occurrences carrying a given hash. That
owner performs the authoritative within-batch deduplication, checks its local
seen chunks, and rejects hashes accepted by earlier batches of the same next
layer.

Thus ownership is exact only to the stored identity key. Unequal semantic
states with the same hash route to the same owner and are then collapsed; the
distributed protocol does not add full-state collision resolution missing from
the single-device path.

## 3. Producer dedup and owner dedup have different scopes

Before routing, each producer calls `get_unique_states` on its locally generated
batch. This can remove duplicates generated by one producer/rank. It cannot
remove equal candidates generated elsewhere.

After routing, the owner calls `get_unique_states` again over all received
records for that batch. It then compares against:

1. owner-local hashes from prior relevant BFS layers;
2. owner-local hashes already accepted from earlier batches of the current
   next layer.

The stages implement:

```text
local compression -> route -> authoritative owner union.
```

Skipping the owner union would be incorrect even if every producer emitted a
locally unique batch.

## 4. Layer closure in the `torchrun` backend

Ranks can have different local frontier sizes. Each computes its local batch
count, then a global maximum through `all_reduce(MAX)`. Every rank executes
exactly that many batch rounds; ranks with no local batch submit empty tensors.

Every round performs the same ordered owner exchange collectives. Only after all
rounds does each owner merge its accepted chunks and compute its final local
next frontier. A global sum gives the next-layer size.

This is the concrete closure mechanism:

```text
same number of collective rounds on every rank
-> all producer batches routed
-> each owner closes local accepted union
-> global next-layer cardinality
-> only then advance the BFS layer.
```

There is no asynchronous early expansion of accepted `F_(d+1)` states while
another `F_d` batch remains. The NCCL collectives and final reductions act as
the level protocol; the final `dist.barrier()` is task-return synchronization,
not the only correctness barrier.

## 5. Visited authority and inverse-closed rolling state

Under `torchrun`, every rank stores only seen hashes it owns. For a general
directed generator set, new owner-local frontier hashes accumulate as chunks,
periodically compacted by exact sorted `unique`.

For an inverse-closed generator set, the code retains only:

```text
previous frontier hashes,
current/next frontier hashes.
```

This is the rolling-window theorem for an undirected support graph: a successor
of `F_d` can only lie in `F_(d-1)`, `F_d`, or `F_(d+1)`. Partitioning does not
change the theorem because every candidate first routes to the authoritative
owner of its hash.

The single-process multi-device backend expresses the same policy as per-owner
`seen_parts`. Its small-frontier fallback checks candidate hashes against the
union of every device's seen partition, so it remains a global membership test
despite running expansion on the primary device.

## 6. Termination and truncation meanings

The distributed traversal sets `bfs_completed=True` only when the global
next-layer size is zero. Other exits remain incomplete prefixes:

- `max_diameter` loop bound;
- `max_layer_size_to_explore` reached;
- user `stop_condition` returns true on any rank.

Under `torchrun`, a stop hook is invoked on every rank after the complete layer
has been gathered to every rank. `all_reduce(MAX)` turns any local true result
into a global stop. Therefore a hook with side effects runs once per rank, not
only on rank zero, and its predicate should be consistent with that API.

Local emptiness never terminates the traversal. Only the globally reduced
next-layer size can prove exhaustion.

## 7. Result gathering is selective and potentially replicated

Owners retain partitioned frontiers for traversal. A full layer is gathered to
every rank only when required for:

- storing a sufficiently small layer;
- returning all layer hashes;
- invoking a stop condition.

The gather uses CPU `all_gather_object` payloads and then copies parts back to
the target device before sorting by hash. This is result materialization, not
the owner-computes hot-path representation. Requests for stored layers or hooks
can therefore introduce full-layer replication absent from a pure traversal
step.

Layer size is always a global sum. Stored layer state order is global hash order,
not discovery order or canonical generator-word order.

## 8. Edge output and batching flags are backend-dependent

`BfsDistributed` returns

```text
edges_list_hashes = None.
```

It does not expose `return_all_edges` or `disable_batching` parameters. Dispatch
in `CayleyGraph.bfs` behaves differently by launch mode:

- ordinary Python with several configured GPUs falls back to the single-device
  `BfsAlgorithm` when `return_all_edges=True` or `disable_batching=True`;
- under `torchrun`, distributed dispatch wins first, then these two keyword
  arguments are removed before calling `BfsDistributed`.

Thus torchrun does not satisfy an all-edges request and does not honor a request
to disable batching through this public dispatch. The call is not rejected; the
options are silently omitted. This is an output/API boundary, not evidence that
returned scalar layer sizes are incorrect.

## 9. Output multiplicity remains scalar

Owner-side `get_unique_states` retains one state per hash. It does not preserve:

- all shortest parents;
- parallel generator-label occurrences;
- shortest-path counts;
- canonical words;
- one serial first-in tree.

The distributed result is naturally a layer-size/state-membership artifact,
with optional gathered hash layers. It should not be interpreted as a richer
shortest-path output merely because routing observed the losing occurrences.

## 10. Failure model boundary

The source assumes successful ordered collectives and live ranks. There is no
logical message ID, retry log, replicated owner state, or recovery protocol in
the inspected path. A rank or collective failure is outside the returned BFS
contract; the final barrier does not turn NCCL execution into a fault-tolerant
consistent-cut protocol.

Likewise, `hash mod world_size` ties ownership to worker count. Changing
`WORLD_SIZE` repartitions every layer and can change order and performance even
when exact scalar frontier sets remain invariant.

## 11. GPU cost coordinates visible in the source

Without timing anything, the code exposes these distinct costs:

```text
local generator-major expansion
local sort/unique
owner sort and state/hash all-to-all
owner receive sort/unique
seen-chunk membership passes
accepted-chunk compaction
global batch-count max
global layer-size sum
optional full-layer CPU object gather and device copy-back.
```

One kernel or one all-to-all timing would not represent a complete layer. Load
balance depends on both frontier owner counts and routed candidate counts;
modulo hashing does not prove either is balanced.

## 12. Rejected implications

- Producer-local unique makes owner-side unique redundant.
- A locally empty rank proves BFS exhaustion.
- The final `dist.barrier()` is the only layer-completion mechanism.
- Multi-GPU routing resolves semantic hash collisions.
- Inverse-closed rolling visited is a distributed approximation.
- `return_all_edges=True` is honored by torchrun because it is accepted by
  `CayleyGraph.bfs`.
- A stop hook runs only on rank zero.
- Gathered hash order is a canonical BFS discovery order.
- Successful NCCL collectives imply retry/failure tolerance.

## 13. Evidence boundary

This note establishes behavior visible in the retained source snapshot. It does
not execute torchrun, validate parity, measure communication, or claim that the
installed/runtime version is identical. The result is a contract audit, not a
runtime or performance experiment and not a proposed implementation change.

## Compact conclusion

CayleyPy distributed BFS is structurally a level-synchronous owner-computes
realization of ordinary BFS: producer compression, hash-owner routing,
authoritative owner union, global layer closure, then advancement. Its exactness
inherits the library's hash-identity premise. Rich outputs, edge enumeration,
fault recovery, canonical parent history, and backend-independent flag behavior
are outside this path's demonstrated contract.
