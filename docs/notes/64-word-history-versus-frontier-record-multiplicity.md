# Word history versus frontier-record multiplicity

REF-027 exposes a distinction that ordinary frontier counters hide: duplicate
word histories can disappear at several different BFS layers before the same
state is counted once.

## Three multiplicities

For a state `v in F_d`, distinguish:

1. **word multiplicity:** number of shortest labeled words reaching `v`;
2. **predecessor-record multiplicity:** number of distinct `(u,label)` records
   from unique `u in F_(d-1)` reaching `v`;
3. **state multiplicity:** one unique endpoint after deduplication.

Two shortest words may merge at an earlier parent and therefore contribute only
one later candidate record. Consequently candidate convergence at depth `d`
does not equal total shortest-word multiplicity at depth `d`.

## The exact Megaminx F3 decomposition

For current Megaminx:

```text
shortest words reaching F3      12,384
candidate records from F2        9,216
unique F3 states                 6,208
```

Therefore:

```text
3,168 word extras were already hidden by F2 state dedup;
3,008 extras remain visible as F3 candidate convergence;
6,176 total shortest-word extras exist at F3.
```

This is not record loss. It is a change of represented object: the frontier
stores states, not the shortest-path DAG or all words.

## Quotienting words by known relations

Counting word multiplicity still does not identify independent relations.
REF-027 forms the trace equivalence generated by

```text
... a b ...  <->  ... b a ... when ab=ba.
```

Every shortest word for each `F3` state belongs to one such equivalence class.
So all 6,176 extras are consequences of known commutation squares. After this
word quotient, the class count equals the state count exactly:

```text
12,384 words -> 6,208 commutation classes -> 6,208 states.
```

At this radius the second arrow performs no further identification.

## Why multiplicities are 1, 2, 3, or 6

A length-three trace under pairwise commutations is a small partially ordered
set. Its distinct word representatives are its linear extensions:

- no usable swap gives one order;
- one independent swap gives two;
- one letter movable around two ordered letters gives three;
- three pairwise commuting letters give all `3! = 6` orders.

REF-027 observes exactly these multiplicities. This turns a duplicate histogram
into a local geometric description rather than a single rejection ratio.

## What a frontier must retain for different outputs

| Desired output | Sufficient retained object |
|---|---|
| distances/frontier sizes | one record per state |
| one shortest path | one parent per state |
| predecessor DAG | every distinct predecessor edge |
| number of shortest paths | predecessor contributions or exact counts |
| all shortest words | full DAG plus enumeration, or explicit histories |
| relation witnesses | enough labeled alternative paths to compare words |

A state-only BFS can be perfectly distance-exact while irreversibly discarding
word multiplicity. This is an output-contract choice, not automatically a bug.

## GPU and multi-GPU interpretation

Hardware counters usually see candidate records, not latent word histories.
Therefore a measured duplicate ratio can understate algebraic path
multiplicity. Earlier dedup is often desirable for state search, but it also
means later instrumentation cannot reconstruct how many word histories were
collapsed without additional metadata.

Across GPUs, the same distinction appears twice:

- local parent dedup may hide histories before routing;
- owner-side dedup may hide convergence between distinct parent states.

Neither count alone describes the shortest-path DAG.

### Saved F4 counter scope: candidate is not every generated transition

Read-only inspection on 2026-08-31 confirms that REF-028 increments
`candidate_records` only after `!distance.contains_key(&child)`. Each unique
`F_3` state still applies every generator before that test. Thus its saved
numbers have the following meanings:

| Quantity | Count | Evidence kind |
|---|---:|---|
| Generator applications in this F3 expansion loop | `6208 * 24 = 148992` | Hand inference from saved F3 size and inspected loop |
| Occurrences returning into `B_3` | `148992 - 139248 = 9744` | Hand difference; no backward/same-level split inferred |
| Outward candidate records, before next-state dedup | `139248` | Saved REF-028 counter |
| Unique `F_4` states | `90144` | Saved REF-028 counter |
| Shortest length-four word occurrences | `274224` | Separate saved word-enumeration result |

The generator-application count covers only that expansion loop, not the
probe's whole workload: initialization, earlier layers, commutation checks,
and separate word enumeration perform additional work. None of these semantic
counts is a device instruction, byte, or timing counter. Reusing the name
"candidate" without identifying where the counter sits would hide 9744
already-generated old-state occurrences in this one layer.

Sources inspected: `experiments/ref028_megaminx_f4_word_classes.rs`,
`experiments/REF-028-megaminx-f4-conjugated-commutators.txt`, and the retained
REF-026/027 F3 evidence. These are historical local artifacts, not freshly
reproduced runtime results or evidence for another move table.

The saved REF-026/027/028 reports record the same input digest, and the current

## Current synthesis

The 3,008 Megaminx `F3` candidate extras were not an unexplained family of new
relations. They were the still-visible part of 6,176 shortest-word extras, all
generated by known commutations. BFS frontier semantics explain why 3,168 of
those histories had already vanished from the candidate stream one layer
earlier.
