# S13 HF v16: upload commit rate limit and pinned-ring exhaustion

Launcher configuration commit `29d950e8d456a53b1adba6207a07768d2f30d2e5`;
runtime `75c4f01c5b8867227434d60a6f36de7fc9a77130`. Real 2xT4,
220M capacity/rank, 256 pinned archive slots/rank, 262144 rows/slot.

Run FAILED. Depth 34 expansion completed; depth 35 had approximately
17.497M states per rank. Native rank 1 reported ARCHIVE_PIN_RING_FATAL;
torchrun stopped the other rank. Peak device consumption was 13989 MiB/rank.

Rank-1 streamer recorded HTTP 429 on the HF staging-branch commit endpoint:
repository commit limit 128/hour. Each 1M-row shard currently calls
`upload_file`, creating its own commit. S13 requires thousands of shards;
this publication design cannot scale under the observed limit.
Rank-0 stream subsequently reported ARCHIVE_TRUNCATED after producer death.
Temporal ordering between network error and native exhaustion is not fully
established from these logs; do not claim rate limiting is the sole throughput
bottleneck. Increasing the pinned ring alone did not solve the problem.

No complete graph publication. Partial staging objects must not be promoted.
Next: decouple object upload from commits and batch commit operations, using
bounded staging with explicit capacity. Validate the publication request count
and throughput before another S13 attempt; no automatic same-config retry.

native depth log and result JSON, both streamer stderr logs, external sampler.
