# dev43 segmented BFS: capacity tuning and eight-GPU checks

This is an experimental development candidate. The default backend remains
`legacy`; `segmented24` and `permutation_bitmap` must be selected explicitly.
These checks do not establish acceptance on B200, complete S14, multi-node
execution, every graph, or the true maximal capacity of a GPU.

## Installed-wheel S12, same host

A single sequential run of each package used the public CayleyPy API, the same
eight RTX 3060 12-GiB devices, same topology and graphs, persistent workers,
`max_capacity`, autotune enabled and the same native binary/library. Graph:
Coxeter S12, 479,001,600 states, 67 layers. Configured segment maximum was
2^32 rows/bank, with actual 1,048,576-row allocation chunks. All layer counts
matched Mahonian numbers, and the final two layers were checked as full state
sets without duplicates; earlier full states were not compared.

| Version | backend / strategy | queue / owner lanes | BFS s | API wall s | autotune s |
|---|---|---:|---:|---:|---:|
| dev42 | segmented24 / warp | 2048 / 1 | 175.557 | 305.997 | 56.848 |
| dev43 | segmented24 / warp | 2048 / 1 | 183.756 | 311.225 | 57.135 |
| dev42 | permutation_bitmap / atomic | 2048 / 1 | 353.618 | 403.352 | 49.070 |
| dev43 | permutation_bitmap / atomic | 8192 / 4 | 128.123 | 187.084 | 58.251 |

Each row is a single observation; the hash difference is not evidence of a
reproducible regression. The bitmap comparison includes the different
configurations selected by the two tuners; it does not isolate queue size from
owner lanes or prove a speedup on another graph. Four shards, initial batch
5957 and exact exchange were used in these S12 runs. A first task can include a
costly transport probe, so API wall time is not just BFS plus autotuning.
Periodic 1-second NVIDIA management samples are not exact transient VRAM peaks;
rank allocations, sample maxima and tuning decisions are included in the
[machine-readable receipts](artifacts/2026-11-22-dev43-s12-exact-evidence.json.gz), SHA-256 `26194e0c95d15049ea7c91018bdaf0cf8957bc353b72e534fb5fbd15d4b1c38b`.

## Large S13 prefix

On the same eight-GPU host, Coxeter S13 was intentionally stopped after
completed depth 38 (`INCOMPLETE/PROFILE_LAYER_LIMIT`); this is not a full
S13 calculation. Every recorded layer size matched the independent Mahonian
oracle. Intermediate full state sets were **not** compared in these runs.
Both used eight shards, four owner lanes, queue 6144, initial batch 8192,
exact exchange, `balanced`, autotune off, and 1,048,576-row allocated
segments with configured 2^32 maximum.

| Backend / strategy | BFS to depth 38 s | Depths 34–38 s | New states in window | Worst 1-s sampled MiB | Max per-rank peak live rows |
|---|---:|---:|---:|---:|---:|
| bitmap / atomic | 627.986 | 304.950 | 1,378,000,276 | 2023 | 110,344,906 |
| hash / warp | 1041.418 | 508.384 | 1,378,000,276 | 5449 | 107,792,853 |

These are single observations and do not predict B200 performance. A short
CPU-only CayleyPy introspection and script preparation overlapped the bitmap
run; a small archive transfer overlapped the early hash prefix. The measured
window sums cannot be interpreted as isolated kernel times. The earlier
[full six-strategy S13 comparison](2026-11-21-s13-prefix.md) uses a different,
older native artifact, and its old hash/warp path predates the deduplication
race fix. Allocation receipts and per-rank samples are included separately.
[Prefix script](artifacts/2026-11-22-dev43-8gpu-s13-prefix.py).

## Ownership and reduced-domain check

On the same installed dev43 native artifact, an S10 subgroup acting on the
first 10 of 14 positions completed on eight GPUs with cyclic and page-64
bitmap ownership. All S10 Mahonian counts and the full last two state sets
matched; intermediate full sets were not compared. The positional-orbit
domain was 3,628,800 IDs and the visited bitmap occupied 56,704 bytes on
each rank. The earlier full-domain implementation allocated 1,362,160,800 bytes
per rank for this case; the numbers are from different source snapshots.

| Ownership | BFS s | Per-rank peak live rows, min–max | Max / mean of per-rank peaks | Remote records sent, total |
|---|---:|---:|---:|---:|
| cyclic | 0.797 | 92,438–95,174 | 1.0146 | 13,063,680 |
| page 64 | 1.255 | 92,349–94,043 | 1.0075 | 18,833,770 |

The two timings are single observations with per-layer and software transport
diagnostics enabled. Per-rank peaks may occur at different times; this ratio is
not a simultaneous layer imbalance. Remote-record counts are software counts,
not measured link bytes. Page 64 was slower and transferred more records on
this workload; cyclic remains the default. Before reduced-domain ranking, the
[earlier skew experiment](2026-11-21-integrated-followup.md) observed 745,192
peak live rows on one rank with cyclic and 93,591 with page 64. These different
artifacts and settings do not isolate the contribution of each change.
[Skew reproduction script](artifacts/2026-11-22-dev43-8gpu-skew.py). The [S13 and skew rank receipts](artifacts/2026-11-22-dev43-s13-skew-evidence.json.gz) have SHA-256 `0366ed157f884919d9914cfa74a78cf942048572a1cecb4da23e8cfe9f56a882`.

## Tuning, capacity and reuse

Previously `max_capacity` implicitly constrained candidate queues and lanes
to its conservative defaults. The new tuner measures additional admitted
candidates while respecting explicit user limits. It ranks them using the
minimum per-rank number of complete segments, a proportional remainder
estimate, then time on a common completed prefix. This is a **heuristic**, not
proof of maximum capacity: hash rounding, shard fragmentation, queues, CUDA,
NCCL and actual free memory matter. Resource errors do not become successful
results.

The cache now identifies effective free memory without separately treating
two already included reusable-memory subtotals as independent capacity. It
still changes when effective free, total or reserved memory changes; live
memory admission runs for production jobs. On two GPUs, after warming the same
memory, hash → bitmap → hash reused the same worker PIDs and the hash profile:
the recorded second hash tuning step fell from 46.89 s on old source to
0.0279 s on new source. That is a controlled comparison, not a promise of
zero startup work: in a cold installed-wheel run, hash → bitmap → hash retuned
because effective free memory had changed by about 94 MB.

For a separate two-GPU S13 hash pressure test, with an intentionally high
10.3 GB per-GPU reserve, queue/lane configurations 2048/1 and 16384/4 both
stopped `INCOMPLETE/RESOURCE_10` after completed depth 20, with matching
Mahonian prefix counts. The result compares that completed prefix; it does not
prove equal ultimate capacity or a complete S13 calculation.

S14/S15 theoretical memory arithmetic and earlier skew/capacity experiments
are in the [integrated evidence report](2026-11-21-integrated-followup.md).
The 2^32 segment boundary has arithmetic and reduced-boundary GPU coverage,
not a physical allocation of 2^32 rows.
